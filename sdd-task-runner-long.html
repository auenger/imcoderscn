SDD Task Runner

Spec-Driven Development — 极简自动化任务执行框架

从 30 个组件到 4 个组件的工程简化之路

问题

旧系统：过度工程的代价

1
组件爆炸

8 模板 + 16 skills + 4 commands + 2 hooks = 30 个组件，维护成本远超实际收益

2
流程过重

每个 feature 要走 branch → worktree → tag → archive 完整生命周期，对于简单任务是大炮打蚊子

3
认知负担

16 个 skill 命令需要记忆，新人上手成本高，调试链路长

核心矛盾：我们需要的是自动化执行，而不是自动化管理的管理系统。
核心思想

SDD — Spec-Driven Development

传统思路

定义流程 → 创建模板 → 配置 hook → 管理状态 → 调度执行 → 归档清理

大量精力花在"管理"本身

SDD 思路

写清楚要做什么（spec）→ 让 Agent 去做 → 检查结果

精力花在"做事"本身

一个 spec = 一个任务：每个任务只需要一个 markdown 文件，包含目标、要求、参考文件和验收标准。调度器读完 spec 就直接派 SubAgent 干活。

Spec 文件

一个 markdown 就是一个任务

spec 模板结构

# Task: 初始化数据库

## 目标
创建 SQLite 数据库 schema，包含职位、公司、搜索记录三张表

## 具体要求
- 使用 SQLAlchemy ORM 定义模型
- 支持 migration 机制
- 表结构参考 docs/db-design.md

## 参考文件
- src/models/ （现有模型目录）
- docs/db-design.md （表结构设计文档）

## 验收标准
- [ ] 三张表创建成功，字段和类型匹配设计文档
- [ ] migration 可重复执行不报错
- [ ] 有基本的索引设置

设计原则：spec 只关心"做什么"，不关心"怎么做"。执行细节由 SubAgent 根据项目现有代码模式自行决定。

创建任务

/new-task — 从想法到工单

Step 1
生成 ID — 读取 queue.yaml，找最大编号 + 1，格式 NNN-kebab-case
Step 2
收集信息 — 交互模式询问目标、要求、参考文件、验收标准；或用 --desc 直接传入
Step 3
写 spec — 创建 sdd-tasks/specs/{id}-{slug}.md
Step 4
入队列 — 追加条目到 queue.yaml，设置 status: pending 和 depends_on
/new-task 初始化数据库                        # 交互收集需求
/new-task 写入种子数据 --depends 001          # 指定依赖
/new-task 搜索API --desc "实现全文检索接口"   # 直接带描述
调度执行

/run-tasks — 自动串行执行器

SCAN
→
PICK
→
MARK RUNNING
→
LAUNCH SUBAGENT
→
COLLECT
→
LOOP

AUTO-LOOP 规则

  • 有 pending 且依赖满足 → 立即执行下一个
  • 不询问用户"是否继续"
  • 只有三种停止条件：全部完成 / 任务失败 / 死锁

依赖检查

  • depends_on 全部 done → 可执行
  • 有 pending/running → 本轮跳过
  • 有 failed → 不可执行（除非 --continue）
  • 检测循环依赖 → 报告死锁
执行引擎

SubAgent — 自主任务执行者

SubAgent 接收的指令

读取 spec 全文作为 prompt → 先看参考文件 → 遵循项目现有代码模式 → 只改 spec 要求的部分 → 返回结构化 JSON 结果

成功返回

{
  "task_id": "003-search-api",
  "status": "success",
  "files_modified": [
    "src/routes/search.py",
    "src/services/search.py"
  ],
  "summary": "实现全文检索 API",

失败返回

{

  "error": "缺少依赖包",
  "partial_files": ["src/routes/search.py"],
  "suggestion": "安装 cursor-pagination 包"
}
对比

新旧系统：从 30 到 4

旧系统（Feature Workflow）

  • 8 个模板文件
  • 16 个 skill 命令
  • 4 个 slash command
  • 2 个 hook 脚本
  • 支持并行、分支、归档
  • 完整的 git 生命周期管理

新系统（SDD Task Runner）

  • 1 个 queue.yaml
  • 1 个 specs 目录
  • 2 个 slash command
  • 2 个 hook 脚本（保证执行完整性）
  • 1 个 queue 模板
  • 纯串行、依赖感知
  • spec 即文档，无额外流程

不是替代，而是分层：旧系统适合大型 feature（多天、多人协作），新系统适合中小型任务（单日可完成、明确的 spec）。两者可以共存于同一项目。

设计哲学

简化的三个原则

1. Spec 即唯一约定

不需要模板、配置、hook。一个 markdown 文件定义了任务的所有信息。Agent 读得懂，人也能 review。

2. 状态集中到单文件

queue.yaml 是唯一的状态源。没有 worktree、branch、tag 的状态散落。想看进度？看这一个文件就够了。

3. 方便扩充和定制

想加功能？改 command 文件。想加验证步骤？在 spec 里写验收标准。框架不挡路，你加什么它就执行什么。

4. 失败也要可读

SubAgent 返回结构化 JSON：成功有文件列表和摘要，失败有错误描述和修复建议。不是黑盒。

SDD Task Runner

1 个队列 + 1 个 specs 目录 + 2 个命令
