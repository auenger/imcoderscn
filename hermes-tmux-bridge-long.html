Architecture Design

Hermes × Claude Code
调度架构

通过 tmux 桥接国内 IM，驱动 Claude Code 执行 Superpowers 工作流

2026.05

Problem

核心问题：国内 IM 无法直连 Claude Code

1
ACP 协议缺失

国内的 IM（钉钉、飞书、企微等）不支持 ACP（Agent Communication Protocol）通讯协议，无法直接与 Claude Code 建立双向通道

2
上下文成本高

如果把 Claude Code 的完整输出塞进 Hermes 上下文，会快速消耗 token 额度，且大部分输出内容对调度决策无用

3
多实例调度需求

团队需要通过 IM 同时调度多个 Claude Code 实例，处理不同的 bug、issue、task，需要统一入口和状态管理

Architecture

整体架构：Hermes 作为调度中枢

用户 IM
→
Hermes Gateway
→
tmux Session
→
Claude Code
→
Skill 执行

核心思路：Hermes 只做输入解析和输出转发两件事，不承载 Claude Code 的执行过程，从而节省上下文空间。

Hermes Gateway

  • 接入钉钉 / 飞书 / 企微
  • 解析用户指令 → 确定目标 Skill
  • 通过 tmux 控制 Claude Code
  • 提取关键输出 → 转发回 IM

Claude Code + Skill

  • 运行在独立 tmux session 中
  • 加载 Superpowers 工作流 Skill
  • 处理 bug / issue / task
  • 完整输出留在 tmux 中
Design

tmux 桥接方案：控制面与数据面分离

控制面（Hermes → tmux）

  • 创建 tmux session 对应每个任务
  • 向指定 pane 发送 Claude Code 命令
  • 触发特定 Skill 的执行
  • 轻量级指令，几乎不占上下文

数据面（tmux → Hermes Gateway）

  • capture-pane 获取 Claude Code 输出
  • 只提取关键结果（状态、摘要）
  • 丢弃中间过程日志
  • 转发精简结果到 IM

关键收益：Claude Code 可能输出数千行内容，但 Hermes 只需捕获最终结论和关键状态变更，上下文消耗降低 90%+。

Workflow

完整工作流：从 IM 消息到任务完成

Step 1
用户在 IM 中发出指令 — 钉钉群里 @Hermes Bot："处理 #1234 bug，使用 bugfix skill"
Step 2
Hermes Gateway 解析意图 — 识别任务类型（bug/issue/task）、目标 Skill、相关上下文参数
Step 3
创建或复用 tmux session — tmux new-session -s task-1234，启动独立的 Claude Code 实例
Step 4
通过 tmux 发送 Skill 命令 — tmux send-keys -t task-1234 '/superpowers-bugfix #1234' Enter
Step 5
Claude Code 执行 Skill 工作流 — 完整的分析、修复、测试流程在 tmux 中独立运行
Step 6
Hermes 轮询捕获输出 — 定期 tmux capture-pane 提取关键状态，检测执行是否完成
Step 7
Gateway 转发精简结果到 IM — 将最终结论、PR 链接、测试状态等关键信息发回钉钉群
Implementation

tmux 命令详解

输入控制

# 创建独立 session
tmux new-session -d -s bug-1234

# 启动 Claude Code
tmux send-keys -t bug-1234 'claude' Enter

# 发送 Skill 指令
tmux send-keys -t bug-1234 \
  '/bugfix --issue=1234' Enter

# 检查 session 状态
tmux list-sessions

输出捕获

# 捕获当前 pane 内容
tmux capture-pane -t bug-1234 -p

# 捕获历史输出
tmux capture-pane -t bug-1234 \
  -p -S -1000

# 捕获并写入文件
tmux capture-pane -t bug-1234 \
  -p > /tmp/output-1234.log

# 检测进程状态
tmux list-panes -t bug-1234 \
  -F '#{pane_dead}'
Skill

Superpowers 工作流 Skill 体系

Bug Fix Skill

接收 bug ID → 定位代码 → 分析根因 → 生成修复 → 运行测试 → 提交 PR

Issue Processing Skill

解析 issue 描述 → 确认需求 → 评估影响 → 生成方案 → 执行实现

Task Execution Skill

拆解任务 → 逐步实现 → 自动化测试 → 文档更新 → 状态同步

Code Review Skill

拉取变更 → 静态分析 → 安全审查 → 性能评估 → 生成 review 意见

每个 Skill 都是一个完整的端到端工作流，Claude Code 在 tmux 中自主执行，无需 Hermes 介入中间步骤。
Optimization

上下文优化：只做输入和输出转发

传统方案（❌ 高成本）

  • Hermes 维护完整对话上下文
  • Claude Code 输出全部传入 Hermes
  • 每个 token 都计入 Hermes 额度
  • 上下文窗口快速耗尽
  • 多任务并行时成本爆炸

tmux 桥接方案（✅ 低成本）

  • Hermes 只存调度元数据
  • 只提取最终状态和结论
  • 中间过程留在 tmux buffer
  • 上下文占用降低 90%+
  • 可并行调度数十个任务

Hermes 的角色：纯粹的路由器和翻译器 — 把 IM 消息翻译成 Claude Code 命令，把 Claude Code 输出翻译成 IM 消息。

Scale

多实例并行：tmux Session 隔离

Hermes
→
tmux: task-001
|
tmux: task-002
|
tmux: task-003
Session 任务类型 Skill 状态
task-001 Bug Fix /bugfix --issue=1234 ✓ 已完成
task-002 Feature /feature --spec=auth-v2 ⟳ 执行中
task-003 Review /review --pr=567 ○ 排队中
每个 tmux session 完全隔离，一个任务的崩溃不影响其他任务。Hermes 通过 session 名称精确路由输入和输出。
Validated

调度脚本就绪：双模式执行引擎

Print 模式（推荐，默认）

  • 一次性任务，执行完自动退出
  • 适合：写代码、修 bug、重构、创建文件
  • 不需要 tmux，直接 claude -p
  • 输出干净，直接拿到结果

✓ 测试通过：文件创建、代码输出都正常

Interactive 模式（tmux）

  • 多轮对话 TUI 会话
  • 适合：探索性编程、需要中间决策的任务
  • 通过 tmux capture-pane 监控
  • 提取关键回复，转发回 IM

→ 适合需要人机协作的复杂任务

Usage

claude-tmux.sh 实战用法

脚本路径: ~/.hermes/scripts/claude-tmux.sh

# 编码任务（默认 print 模式）
claude-tmux.sh <session名> "任务描述" /项目路径 300

# 多轮交互（interactive 模式）
claude-tmux.sh <session名> "任务描述" /项目路径 300 interactive
场景 1
修 bug — claude-tmux.sh fix-login "修复登录页空指针异常" /app 300
场景 2
新功能 — claude-tmux.sh feat-pay "实现微信支付回调" /api 600
场景 3
探索重构 — claude-tmux.sh refactor "分析订单模块重构方案" /core 600 interactive
Summary

设计总结

1
Hermes 作为轻量 Gateway — 只做输入解析和输出转发，不承载执行过程
2
tmux 桥接 ACP 缺口 — 用 tmux send-keys / capture-pane 替代 ACP 协议
3
双模式执行引擎已就绪 — print 模式处理一次性任务，interactive 模式处理多轮对话
4
方案已验证通过 — claude-tmux.sh 脚本测试通过，可接入钉钉等国内 IM

一句话总结：用最轻的中间层打通国内 IM 和 Claude Code，让团队通过钉钉就能驱动 AI 完成研发任务。
