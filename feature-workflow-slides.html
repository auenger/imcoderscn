定位

Feature Workflow 是什么

一套基于 Claude Code 的完整功能开发工作流系统。通过 Command、Agent、Skill 三层架构，实现并行开发、状态追踪、自动化质量保障，让 AI 从"问答工具"变成"开发搭档"。

核心价值：AI 不再只是回答问题，而是按照结构化流程自主完成需求分析、代码实现、质量验证和归档，全程无需人类干预。

并行开发

多个 Feature 通过 git worktree 物理隔离，同时推进

状态管理

集中式 queue.yaml 统一追踪 active / pending / blocked / completed

质量门禁

6 维度文档审查 + Gherkin 验收标准 + Playwright 自动测试

知识积累

归档元数据 + 渐进式加载，历史经验自动赋能新需求

架构

三层架构设计（v3）

基于 Claude Code v2.1.x 的 Command + Agent + Skill 分层设计：

用户 → /dev-agent (Command, 主上下文)
         │ ← 调度：读取队列、评估依赖、批量派发
         │
         └── Agent Tool → DevSubAgent (独立 200k 上下文)
                              ├── Skill → /start-feature
                              ├── Skill → /implement-feature --auto
                              ├── Skill → /verify-feature --auto-fix
                              └── Skill → /complete-feature --auto

Command 层

/dev-agent 作为入口，负责读取 queue.yaml、评估依赖关系、批量派发任务。运行在主上下文，掌控全局调度。

Agent 层

DevSubAgent 独占 200k 上下文，不污染主对话。通过 Skill Tool 调用预加载的 Skill，是"编排器"而非"实现者"。

关键设计：Skill 是原子能力单元，Agent 是编排器，Command 是入口和调度中心。每层职责清晰，不重复实现逻辑。

理念

核心理念

一个 Feature = 一个 Worktree = 一个独立开发环境。每个需求在自己的 git 分支和 worktree 中完整闭环，互不干扰。
1
隔离性

每个 Feature 有独立的 worktree 目录、独立分支、独立上下文。并行开发不会互相污染代码。

2
文档驱动

每个 Feature 包含 spec.md（需求规范）、task.md（任务清单）、checklist.md（质量检查表）三份文档，AI 按文档执行。

3
全自动原则

DevSubAgent 全程无人值守：测试失败 → 自动修复 → 重跑；Rebase 冲突 → 智能分析 → 自动合并。多次重试失败才返回诊断报告。

并行

并行开发能力

基于 git worktree 的物理隔离，多个 Feature 同时推进，互不干扰。

/dev-agent → 批量调度
  ├── DevSubAgent-1 (feat-auth)     ← worktree: project-feat-auth/
  │     ├── /start-feature
  │     ├── /implement-feature --auto
  │     └── /verify-feature --auto-fix
  ├── DevSubAgent-2 (feat-ui)       ← worktree: project-feat-ui/
  │     ├── /start-feature
  │     └── /implement-feature --auto
  └── DevSubAgent-N ...

隔离机制

  • 每个 Feature 独立 worktree 目录
  • 独立 git 分支，代码完全隔离
  • 独立 200k 上下文，不互相干扰
  • 完成后 worktree 和分支自动清理

调度策略

  • max_concurrent 控制并行上限
  • 自动评估 Feature 间依赖关系
  • 支持父子关系，子 Feature 按序执行
  • run_in_background 批量派发
质量

自动化质量保障

6 维度文档审查开发前的质量门禁
Gherkin 验收标准Given-When-Then 结构化场景
多类型验收Backend 代码分析 / Frontend Playwright / Fullstack 混合
证据保存截图 + Trace + 验收报告，可回溯

/review-spec 6 维度评分（100 分制）：清晰度、完整性、一致性、可行性、Gherkin 质量、风险评估。低于阈值自动 block，支持 --fix 自动修复。

验收方法

自动检测 Feature 类型，前端用 Playwright MCP 执行浏览器测试，后端用 AI 代码分析验证 Gherkin 场景。

自动修复

测试失败 → 自动修复代码 → 重跑测试（最多 2 次）。Lint 报错 → 修复 → 重跑。多次重试失败才返回 error + 详细诊断。

blocked/block-feature 阻塞reason, dependencies

queue.yaml 支持父子关系管理：大型需求拆分后，父 Feature 作为模块索引，子 Feature 按依赖顺序依次执行。
拆分

智能需求拆分

当需求识别到 3 个以上用户价值点 时，自动建议拆分。拆分原则是按用户价值而非技术层。

正确：按用户价值

  • feat-auth-register → 用户能注册
  • feat-auth-login → 用户能登录
  • feat-auth-permission → 用户能管理权限

错误：按技术层

  • feat-auth-db → 数据库设计
  • feat-auth-api → API 开发
  • feat-auth-ui → 前端界面
阶段 1
/split-feature — 分析 spec，按业务域拆分为子 Feature，原 Feature 转为模块索引，更新 queue.yaml
阶段 2
/enrich-feature — 渐进式归档加载（Level 1 索引扫描 → Level 2 SubAgent 深度加载），充实三文件内容

拆分规则：每个子需求独立可交付价值，子需求间无循环依赖，数据库/实体按需创建。

归档

归档与知识积累

完成的 Feature 不会消失——丰富的元数据被保存到 archive-log.yaml，成为团队的知识资产。

归档元数据

keywords[] category value_points related_features[] stats (commits/files/+/−) verification status

Level 1
索引层 — /query-archive 读取 archive-log.yaml 索引，按关键词/分类/关联过滤，毫秒级响应
Level 2
深度加载 — SubAgent 按需加载完整归档内容，提取实现模式、历史教训、代码结构
自动关联机制：/new-feature 自动搜索关联归档填充 Dependencies；/start-feature 自动加载依赖 Feature 的实现上下文。历史经验自动赋能新需求。
