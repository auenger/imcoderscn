Hermes × cc-connect
远程调度方案

用 cc-connect 直连 Claude Code，配合 Hermes 构建完整的远程任务调度生态

2026.05

Problem

tmux 桥接方案的局限性

1
自建脚本维护成本高

claude-tmux.sh 需要自己维护 send-keys / capture-pane 逻辑，解析 Claude Code 的 TUI 输出，遇到版本更新容易失效

2
仅支持单通道调度

tmux 方案一次只能对接一个 IM 平台，缺乏多平台统一接入能力，钉钉、飞书、企微需要分别开发适配

3
缺乏会话与权限管理

无法精细控制谁可以触发任务、任务执行中的状态追踪、会话切换等企业级需求

核心矛盾：tmux 方案解决了"能不能用"的问题，但离"好用、稳定、可扩展"还有差距。

Solution

cc-connect — 开源 IM ↔ Agent 桥接层

12 个 IM 平台
↔
cc-connect
↔
10+ AI Agent

核心能力

  • 支持飞书 / 钉钉 / 企微 / Slack / Telegram 等 12 个平台
  • 支持 Claude Code / Codex / Cursor / Gemini CLI 等 Agent
  • 大多数平台无需公网 IP
  • 流式回复、语音、图片、文件传输

企业级特性

  • 多项目隔离，一个进程管理多个 Agent
  • 会话管理：/new /switch /list 完整控制
  • 权限模式：/mode yolo|default 灵活切换
  • 定时任务、Provider 管理、Web Admin UI
cc-connect 是 MIT 协议的开源项目，Go 语言编写，npm / Homebrew 一行安装，解决了从"自己造轮子"到"用成熟方案"的跨越。

Comparison

tmux 桥接 vs cc-connect 对比

维度 tmux 桥接 cc-connect
连接方式 send-keys / capture-pane 模拟终端操作 协议级直连 Agent stdin/stdout
IM 平台 需自行开发每个平台适配 内置 12 个平台，开箱即用
公网 IP 需要自己解决 大多数平台无需公网 IP
会话管理 通过 tmux session 名手动管理 /new /switch /list 完整管理
权限控制 无 admin_from + /mode 权限体系
多项目 每个任务一个 tmux session 一个进程管理多个 Agent 实例
流式输出 需轮询 capture-pane 原生流式回复到 IM
维护成本 自建脚本，需要自己跟进变化 开源社区维护，持续更新

结论：tmux 方案适合快速验证 PoC，cc-connect 适合生产级部署。两者可以共存，根据场景选择。

Features

cc-connect 核心能力矩阵

会话管理

/new 创建新会话，/list 查看所有会话，/switch 切换上下文。自动轮转防止上下文漂移

权限体系

admin_from 白名单控制特权用户，/mode 切换权限等级，支持 OS-User 级隔离

定时任务

自然语言设置 cron：/cron add 0 6 * * * 每天早6点总结 GitHub Trending

多项目架构

一个 cc-connect 进程管理多个 Agent + 平台组合，每个项目独立配置和工作目录

Provider 管理

/provider list 查看可用 Provider，/provider switch 运行时切换 API 提供商

附件回传

Agent 生成的截图、图表、PDF 等文件自动发送回 IM 对话，支持飞书和 Telegram

Web Admin UI

内嵌管理面板，可视化创建项目、管理 Provider、监控会话、编辑定时任务

多语言支持

原生支持中英日西 5 种语言界面，跨地区团队无障碍使用

Integration

Hermes + cc-connect：双层调度架构

用户指令
→
Hermes Agent
→
cc-connect
→
Claude Code

Hermes Agent（任务编排层）

  • 接收复杂任务指令，拆解为子任务
  • 决定任务路由：哪个 Agent 处理什么
  • 维护任务状态机：排队 → 执行中 → 完成
  • 跨任务编排：A 任务完成后触发 B 任务
  • 结果聚合：汇总多个 Agent 的输出

cc-connect（通道连接层）

  • 负责 IM ↔ Agent 的消息双向传输
  • 管理会话生命周期和上下文
  • 处理权限、Provider、流式输出
  • 定时任务执行和结果回传
  • 多项目隔离和并发控制

分工原则：Hermes 负责"做什么"（任务编排和决策），cc-connect 负责"怎么做"（通道连接和执行）。

Deployment

实战部署方案

安装 cc-connect

# npm 一行安装
npm install -g cc-connect

# 或 Homebrew
brew install cc-connect

# 或直接下载二进制
curl -L -o cc-connect \
  https://github.com/chenhg5/\
cc-connect/releases/latest/\
download/cc-connect-linux-amd64
chmod +x cc-connect

配置项目

# Web UI 配置（推荐）
cc-connect web

# 或手动编辑配置
mkdir -p ~/.cc-connect
cp config.example.toml \
  ~/.cc-connect/config.toml
vim ~/.cc-connect/config.toml

# 启动服务
cc-connect
Step 1
部署 cc-connect — 在开发机上安装并配置 IM 平台接入
Step 2
配置 Hermes — 将 Hermes 的任务输出指向 cc-connect 的消息通道
Step 3
验证链路 — 在 IM 中发送测试指令，确认完整的 指令→执行→回传 链路

Summary

设计总结

1
cc-connect 替代 tmux 桥接 — 协议级直连 Agent，12 个 IM 平台开箱即用
2
Hermes 专注任务编排 — 不再做通道适配，专注于"做什么"的决策层
3
三层解耦架构 — 接入层 / 调度层 / 执行层独立演进，灵活替换
4
生产级可用 — 企业级权限、会话管理、定时任务，满足团队协作需求

一句话总结：用开源成熟的 cc-connect 替换自建 tmux 桥接，让 Hermes 专注调度编排，构建稳定、可扩展的远程任务调度生态。
