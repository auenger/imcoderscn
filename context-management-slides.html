AI Engineering

Context 管理
AI 工程里最被低估的核心能力

大多数人以为 prompt 工程就是写好一段话。
但真正决定 AI 输出质量的，是你往上下文里塞了什么、没塞什么、以什么顺序塞的。

杨正武 · 2026.04

真实场景

一个被反复验证的事实

🪲
你把整个项目丢给 AI，说「帮我改一下登录页面的 bug」。AI 迅速改完了登录页面，但顺手把旁边的支付模块也「优化」了一下。

它懂你的需求。但你的 context 里塞了太多跟登录页面无关的东西，它的注意力被分散了。就像让一个人在嘈杂的工地里念电话号码，能听到，但记不全。

Context 的质量决定了 AI 输出的质量，而 context 的质量跟 token 数量几乎无关。

核心认知

注意力是有预算的

误解：容器模型

Context window 是一个容器，往里面装的信息越多，AI 就越「了解」你的项目。

真相：预算模型

Context window 是一个注意力预算池，每一条信息都在消耗这份预算。信息越多 ≠ 质量越好。

你在 Cursor 或 Claude Code 里打开一个项目——当前编辑的文件、@ 引入的文件、项目结构、linter 错误、terminal 输出、git diff、system prompt——每一项都在消耗注意力预算。
论文实证

Lost in the Middle

2023 年 Stanford 等机构实验：把关键信息放在 context 的不同位置，测量模型回答准确率。

开头
~95%
中间
~55%
结尾
~90%

当你把 200K tokens 一股脑塞给 AI 时，真正被它「看到」的信息，可能只有开头和结尾的各 20%。中间那 60%，它大概是扫了一眼就过去了。

Self-attention 机制天然给首尾位置更高权重，这不是 bug，是 Transformer 架构的固有特性。

信噪比

Context 管理的本质

把 context 管理理解为 token 管理，是把问题想浅了。真正的 context 管理是在做信噪比优化。

策略 A：大而全

  • 整个项目文件结构
  • bug 所在文件 800 行代码
  • 类型定义 + 测试文件
  • git diff + README
  • package.json

策略 B：精准裁剪

  • bug 相关函数 + 上下文（50 行）
  • 输入输出类型定义
  • 触发 bug 的测试用例
  • 一行项目背景说明

AI 在 50 行代码里找 bug，和在 800 行代码里找 bug，是完全不同的任务。前者它真的在读每一行，后者它大概率只扫了前 200 行和后 200 行。

失败模式

需求偏离：最常见的翻车方式

需求偏离不是一步到位的，而是一个渐变过程：

Step 1
明确任务 — 给了一个清晰的需求
Step 2
顺便改改 — AI 觉得「一起改了会更好」
Step 3
牵连扩散 — 改了文件 A，文件 B 也需要调整
Step 4
继续顺便 — 新的 context 又触发了新的「顺便」
Step 5
彻底跑偏 — 你要的是改按钮颜色，AI 重构了整个组件体系

人类漂移了自己能意识到，AI 漂移了它完全不知道，还觉得自己做得很好。

防御策略

怎么防住需求偏离

缩小 context 边界

只给跟当前任务相关的文件和代码。「可能有用」和「确定有用」之间隔着巨大的信噪比差距。

显式声明约束

「只修改这个函数。不要重构。不要优化。只修 bug。」看似啰嗦，实际是在帮 AI 划定注意力边界。

分步执行

大任务拆成小步骤，每一步只加载必要的 context。做完一步清掉无关上下文，再做下一步。

及时纠偏

AI 开始「自由发挥」时马上打断。不要指望它自己绕回来。每发现一次偏离就是一次重新校准的机会。

工程模式

五个 Context 管理模式

1. 渐进式加载

不一次性塞满，按需加载。第一轮任务描述 + 核心文件，第二轮相关依赖，第三轮测试和边界情况。

2. 上下文裁剪

定期清理已完成、不再需要的上下文。已修复的报错？删。上个任务的讨论？删。用完的文档？删。

3. 结构化注入

不是堆砌，是有结构的组织：任务 → 约束 → 相关代码 → 测试用例。帮 AI 快速定位每部分的角色。

4. 场景隔离

A 项目偏好不带入 B 项目。昨天的临时决策不自动出现在今天。跨场景流动看起来像「智能」，实际往往是「污染」。

5. 上下文预算

简单 bug 修复 500-1K tokens · 功能开发 2-5K tokens · 架构重构 5-10K tokens。一个简单修复要 20K tokens？要么任务拆分有问题，要么项目结构该优化了。

实战案例

Claude Code 的 Context 分层架构

Claude Code 的 context 不是静态字符串，是每次 API 调用时动态组装的六层结构：

L1
System Prompt — 身份声明 + 编码哲学 + 权限规则 + 风控约束，约 3-4K tokens
L2
Tool Definitions — 内置工具 + MCP 工具定义，约 20-50K tokens（MCP 按需加载 stub）
L3
CLAUDE.md + Memory — 全局 → 用户 → 项目 → 子目录，按层级拼接注入
L4
Dynamic Attachments — 日期、git status、plan 状态、技能列表，通过 <system-reminder> 注入
L5
Tool Visibility — 动态控制模型能看到哪些工具，不可见 = 不可调用
L6
Cache Optimization — 静态内容前置，动态内容后置，KV cache 复用率最大化
Context 预算

你的输入到底去了哪里

Claude Code 200K tokens 的 context window 真实分配（/context 命令输出）：

System Prompt
3.1K
Tool 定义
19.8K
MCP 工具
26.5K
Memory/CLAUDE.md
4K
你的对话
?K

还没开始打字，25-50% 的 context 已经被系统占满。MCP 工具定义一个大就能吃掉 26K tokens。你以为的「200K 窗口」实际可用空间远比想象中小。

缓存策略

静态内容（system + tools + CLAUDE.md）前置，共享 KV cache。动态内容后置，每次只需重新计算尾部。

Compaction

接近上限时自动压缩历史对话为摘要，但复用相同前缀缓存，不浪费已计算的 KV cache。

认知升级

从「写好 prompt」到「管好 context」

Prompt engineering 这个词容易让人产生错觉，以为 AI 工程的核心就是写好一段话。Prompt 只是 context 的一个组成部分。真正的能力在于：你知道在什么时间点，用什么结构，往 AI 的视野里放什么信息，不放什么信息。

这个能力的背后，是对注意力机制的直觉理解：

1
注意力是有限的

不可能同时关注所有信息，预算用完就没有了

2
注意力是不均匀的

开头和结尾的信息天然获得更高权重，中间的容易被忽略

3
注意力是容易被带偏的

一条无关的信息不只是浪费预算，它在主动拉低整体输出质量

结语

Context window 不是容器，
是注意力预算

你管理 context，本质上是在帮 AI 管理它的注意力。

做不好这件事的人，会在 AI 的「自由发挥」里反复踩坑。
做好这件事的人，会让 AI 的输出看起来像是它真的「懂」你的项目。

区别不在于 AI 的能力，在于你往它的视野里放了什么。
