Feature Workflow：基于 Worktree 的多特性并行开发范式

2026年3月13日
杨正武
工作流Git Worktree并行开发多AgentAILock-Step

引言

在 AI 辅助开发的实际应用中，多特性并行开发面临几个核心问题。不同需求的代码会相互干扰，AI 容易产生上下文混淆。传统分支切换方式会导致工作进度丢失。多个 AI Agent 同时工作时，代码冲突难以避免。需求状态管理混乱，无法追溯开发历史。

为了解决这些问题，我设计了 Feature Workflow。这是一个融合了 Bmad 和 OpenSpec 优秀理念的工作流范式，基于 Git Worktree 实现真正的物理隔离，支持多 Agent 并行开发，从根本上避免了代码冲突问题。

Worktree 物理隔离

传统开发方式的问题

传统 Git 工作流使用分支隔离代码，但开发环境共享同一个工作目录。

OA_Tool/                    # 唯一的工作目录
├── src/
├── package.json
└── .git/

# 切换分支时的困境
git checkout feature/auth
# 当前未提交的代码被覆盖，需要 stash 或 commit
# 开发一半的 dashboard 功能无法保留

这种方式导致三个问题。切换分支会丢失未完成的工作进度。无法同时开发多个需求。AI 上下文在分支切换时容易混淆。

Worktree 的物理隔离方案

Git Worktree 允许在同一个仓库下同时检出多个分支到不同目录。

OA_Tool/                        # 主仓库 (main 分支)
├── src/
├── package.json
└── feature-workflow/

OA_Tool-feat-auth/              # Worktree 1 (feature/auth 分支)
├── src/auth/                   # 独立的代码副本
├── .git/                       # 共享 Git 数据库
└── features/
    └── active-feat-auth/
        ├── spec.md
        ├── task.md
        └── checklist.md

OA_Tool-feat-dashboard/         # Worktree 2 (feature/dashboard 分支)
├── src/dashboard/              # 独立的代码副本
└── features/
    └── active-feat-dashboard/
        ├── spec.md
        ├── task.md
        └── checklist.md

每个 worktree 有独立的文件副本和 HEAD，但共享同一个 Git 数据库。这带来了几个关键优势。

开发环境完全隔离

不同需求的代码互不干扰，可以真正并行开发。

# 终端 1：开发认证功能
cd OA_Tool-feat-auth
npm run dev
# 运行在 3000 端口

# 终端 2：开发仪表盘功能
cd OA_Tool-feat-dashboard
npm run dev
# 运行在 3001 端口

无需频繁切换分支，每个需求有独立的开发服务器。AI Agent 可以在不同的 worktree 中并行工作，上下文完全隔离。

独立的测试验证

每个 worktree 有独立的测试环境，证据收集互不干扰。

OA_Tool-feat-auth/
├── e2e/
│   └── auth.spec.ts           # 只测试认证功能
└── evidence/
    ├── screenshots/
    └── traces/

OA_Tool-feat-dashboard/
├── e2e/
│   └── dashboard.spec.ts      # 只测试仪表盘功能
└── evidence/
    ├── screenshots/
    └── traces/

Playwright 测试可以并行执行，截图和 trace 文件隔离存储，不会相互覆盖。

安全的合并策略

传统方式直接合并到 main 分支，冲突在 main 分支解决，容易污染主干代码。

Worktree 方式采用 rebase 策略，冲突在 feature 分支内解决。

feature/auth 分支
    ↓ git rebase main
feature/auth 分支 (包含所有 main 的最新变更)
    ↓ 解决冲突 (在 feature 分支内)
feature/auth 分支 (冲突已解决)
    ↓ git merge --ff-only
main 分支 (快速前进，干净合并)

main 分支始终保持干净状态，冲突解决在 feature 分支完成，解决后可以重新验证。

多特性并行开发

并行控制机制

Feature Workflow 通过 queue.yaml 管理需求队列，config.yaml 控制并行数量。

# config.yaml
parallelism:
  max_concurrent: 2              # 最多同时开发 2 个需求

# queue.yaml
active:
  - id: feat-auth
    name: 用户认证
    priority: 90
    worktree: ../OA_Tool-feat-auth
    branch: feature/auth
    status: implementing

  - id: feat-dashboard
    name: 仪表盘
    priority: 80
    worktree: ../OA_Tool-feat-dashboard
    branch: feature/dashboard
    status: implementing

pending:
  - id: feat-notification
    name: 消息通知
    priority: 70
    dependencies: [feat-auth]     # 依赖认证功能

只有 active 数量小于 max_concurrent 时，才能从 pending 启动新需求。依赖关系确保前置需求完成后才能启动后续需求。

需求生命周期

每个需求经历完整的生命周期管理。

/new-feature        创建需求文档
     ↓
pending-feat-xxx/   进入等待队列
     ↓
/start-feature      创建 worktree 和分支
     ↓
active-feat-xxx/    进入开发状态
     ↓
/implement-feature  AI 实现代码
     ↓
/verify-feature     运行测试验证
     ↓
/complete-feature   合并到 main 并归档
     ↓
archive/
└── done-feat-xxx/  归档所有文档和证据

每个阶段都有对应的命令和状态文件，确保流程可追溯。

多 Agent 并行架构

主从式 Agent 设计

Feature Workflow 采用主从式 Agent 架构实现多特性并行开发。

┌─────────────────────────────────────────────────────────────┐
│ 主 Agent (无状态，可恢复)                                    │
│                                                              │
│ 职责：                                                        │
│ 1. 读取 queue.yaml 获取 active features                     │
│ 2. 检查每个 .status 文件判断当前状态                         │
│ 3. 启动独立的 Feature Agent 进程                             │
│ 4. 监控进度，处理阻塞和错误                                   │
│                                                              │
│ 特点：                                                        │
│ - 上下文极小，只读取 .status 文件                            │
│ - 可随时中断和恢复                                           │
│ - 不直接参与代码实现                                         │
└─────────────────────────────────────────────────────────────┘
         │ 启动独立进程
         │ ./scripts/start-feature-agent.sh feat-auth &
         ▼
┌─────────────────────────────────────────────────────────────┐
│ Feature Agent (独立进程，自治)                               │
│                                                              │
│ 生命周期：implement → verify → complete → 退出              │
│                                                              │
│ 输出：                                                       │
│ - .status (结构化状态文件)                                   │
│ - .log (日志 + EVENT token)                                 │
│                                                              │
│ EVENT Token:                                                 │
│ - EVENT:START feat-auth                                     │
│ - EVENT:STAGE feat-auth implement                           │
│ - EVENT:PROGRESS feat-auth 3/5                              │
│ - EVENT:BLOCKED feat-auth "reason"                          │
│ - EVENT:COMPLETE feat-auth feat-auth-20260305              │
└─────────────────────────────────────────────────────────────┘

状态文件设计

每个 Feature Agent 通过 .status 文件向主 Agent 报告状态。

# features/active-feat-auth/.status
feature_id: feat-auth
feature_name: 用户认证
status: implementing              # started | implementing | verifying | completing | blocked | done
stage: implement                  # init | implement | verify | complete
progress:
  tasks_total: 5
  tasks_done: 3
  current_task: "实现登录 API"
started_at: 2026-03-05T10:00:00Z
updated_at: 2026-03-05T10:30:00Z

# 完成时添加
completion:
  duration: "2h 30m"
  commits: 5
  tag: feat-auth-20260305

# 阻塞时添加
blocked:
  reason: "Rebase 冲突"
  stage: "complete"
  needs_help: true

主 Agent 通过轮询 .status 文件监控进度，不需要维护内存状态。任何时候被中断，重新读取文件即可恢复。

EVENT Token 可观测性

Feature Agent 在 .log 文件中输出标准事件。

EVENT:START feat-auth
EVENT:STAGE feat-auth implement
EVENT:PROGRESS feat-auth 1/5
EVENT:PROGRESS feat-auth 2/5
EVENT:PROGRESS feat-auth 3/5
EVENT:BLOCKED feat-auth "API 依赖缺失"
EVENT:RESOLVED feat-auth
EVENT:PROGRESS feat-auth 4/5
EVENT:PROGRESS feat-auth 5/5
EVENT:STAGE feat-auth verify
EVENT:STAGE feat-auth complete
EVENT:COMPLETE feat-auth feat-auth-20260305

这些事件方便调试和审计，可以通过 grep "^EVENT:" .log | tail -10 快速查看最近发生的事情。

代码冲突解决方案

物理隔离避免冲突

Worktree 机制从根本上避免了开发时的冲突。

传统方式 (同一工作目录):
┌─────────────────────────────────────┐
│ OA_Tool/                            │
│  └── src/                           │
│      ├── auth.ts    ← Agent A 修改  │
│      └── dash.ts    ← Agent B 修改  │
└─────────────────────────────────────┘
问题：两个 Agent 同时修改 src/utils.ts
      → 代码覆盖，逻辑冲突

Worktree 方式 (独立工作目录):
┌─────────────────────────────────────┐
│ OA_Tool-feat-auth/                  │
│  └── src/auth.ts    ← Agent A       │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│ OA_Tool-feat-dashboard/             │
│  └── src/dash.ts    ← Agent B       │
└─────────────────────────────────────┘
优势：两个 Agent 操作不同文件副本
      → 不会有冲突

依赖关系管理

通过 dependencies 字段管理需求间的依赖关系。

# queue.yaml
pending:
  - id: feat-auth-register
    name: 用户注册
    dependencies: []

  - id: feat-auth-login
    name: 用户登录
    dependencies: [feat-auth-register]    # 依赖注册功能

  - id: feat-auth-permission
    name: 权限管理
    dependencies: [feat-auth-login]       # 依赖登录功能

启动需求时检查依赖，只有所有依赖都已完成才能启动。这确保了开发顺序的正确性，避免了因依赖未就绪导致的代码冲突。

合并前冲突检测

在 complete-feature 流程中加入合并前冲突检测。

# 在合并到 main 之前
git fetch origin main
git rebase origin/main

# 检测是否有冲突
if git ls-files -u | grep -q .; then
  echo "检测到冲突，需要先解决"
  git diff --name-only --diff-filter=U
  exit 1
fi

# 无冲突才能继续
git merge --ff-only main

冲突在 feature 分支内解决，解决后可以重新运行测试验证。main 分支始终保持干净状态，不会被冲突污染。

文件重叠预警

系统可以检测多个活跃 worktree 是否修改了相同的文件。

# config.yaml
conflict:
  check_before_merge: true           # 合并前检测
  notify_on_overlap: true            # 文件重叠时提醒

当检测到两个 active features 可能修改相同文件时，系统提前预警，建议调整开发顺序或进行代码拆分。

Bmad 与 OpenSpec 的融合

Bmad 的文档驱动理念

Bmad 强调用 Markdown 文档作为单一数据源。所有信息都在文档中，AI 通过阅读和写入文档来完成任务。

Feature Workflow 借鉴了这个理念，每个需求包含三个核心文档。

features/active-feat-auth/
├── spec.md              # 需求规范（Gherkin 验收场景）
├── task.md              # 任务列表（可勾选的清单）
└── checklist.md         # 检查清单（代码质量、测试覆盖）

spec.md 定义需求要达成的目标，task.md 分解实现步骤，checklist.md 验证完成质量。AI 完全基于这些文档工作，工作流程清晰可见。

OpenSpec 的结构化规范

OpenSpec 强调用结构化的规范描述需求，确保输出质量可预测。

Feature Workflow 引入了 Gherkin 格式的验收场景。

## 验收标准 (Acceptance Criteria)

### 用户故事
作为 用户，我希望 登录系统，以便 访问受保护的功能。

### Gherkin 验收场景

#### 场景 1: 用户登录成功
```gherkin
Given 用户在登录页面
When 用户输入正确的用户名和密码
Then 页面跳转到首页
And 显示欢迎消息

场景 2: 用户登录失败

Given 用户在登录页面
When 用户输入错误的用户名或密码
Then 显示错误提示
And 保持在登录页面


结构化的验收场景让 AI 能够准确理解需求，避免因歧义导致的实现偏差。验证时可以直接用 Playwright MCP 执行这些场景。

### AILock-Step 协议的执行保证

整个工作流基于 AILock-Step 协议实现。

```yaml
# implement-feature 执行流程
STP-001: 读取 spec.md 和 task.md
STP-002: 分析项目上下文
STP-003: 逐项实现任务
  └─ 每个任务都是独立的状态锚点
STP-004: 运行测试验证
STP-005: 更新 .status 文件
  └─ 支持断点续传

状态锚点强制线性执行，AI 不能跳过步骤。每个状态锚点都关联物理存盘点，即使执行中断也能精准恢复。

实际应用效果

OA_Tool 项目实践

OA_Tool 是一个协作工具平台，使用 Feature Workflow 进行开发管理。

并行开发场景

同时开发三个特性：用户认证、仪表盘、消息通知。三个 AI Agent 在各自的 worktree 中并行工作，互不干扰。

效果评估

开发效率提升明显。多个特性可以真正并行推进，不用等待前一个特性完全完成。AI 输出质量更加稳定，每个需求有明确的验收标准。代码冲突大幅减少，Worktree 物理隔离从根本上避免了问题。

可维护性提升

所有特性都遵循相同的开发模式，新成员快速上手。历史项目容易理解，每个完成的特性都有完整的归档记录。重构风险可控，可以通过 tag 快速查看任何历史版本的代码。

完整的追溯能力

每个完成的特性都会创建 Git Tag（如 feat-auth-20260305），保留完整的验证证据（截图、trace、测试报告），归档所有文档（spec、task、checklist）。

features/archive/done-feat-auth-20260305/
├── spec.md                    # 需求文档（包含合并记录）
├── task.md                    # 任务清单
├── checklist.md               # 检查清单
└── evidence/                  # 验收证据
    ├── verification-report.md
    ├── screenshots/
    └── traces/

通过 archive-log.yaml 可以快速查找任何历史特性，通过 Git tag 可以快速恢复任何历史代码。

未来方向

与 Claude Code 原生 Worktree 结合

Claude Code 从 v2.1.50 开始原生支持 --worktree 参数。可以在 worktree 内直接启动 Claude 会话。

# start-feature 创建 worktree 后
cd ../OA_Tool-feat-auth
claude  # 在 worktree 里启动 Claude 会话

增强冲突预警

计划实现文件重叠预警机制。当检测到多个 active features 可能修改相同文件时，提前通知开发者调整策略。

更多技能模块

当前实现了基础的特性开发技能。未来计划添加代码重构技能、性能优化技能、安全审计技能。每个新技能都是一个完整的 AILock-Step 执行流程。
