AgentsZone

为什么要再做一个
Agent 通讯平台

当 IM 接入已经"够用"的时候，我为什么还要造轮子

个人项目 · 2026.4

现状

Agent 接入 IM 已经很成熟了

OpenClaw、Hermes、各种 Claw 产品，接飞书、钉钉、Slack、Discord……看起来通讯问题已经解决了。

IM 接入能做的事

  • 消息收发、@提及触发 Agent
  • 多平台统一入口
  • 用户无需安装新 App
  • 天然的消息通知能力

IM 接入做不到的事

  • 内网隔离环境无法使用
  • 无法管理任务生命周期
  • Agent 间无法结构化通信
  • 数据必须经过第三方
IM 是一个优秀的「人对人」通讯层，但 Agent 需要的远不止消息转发。
问题

五大场景 IM 搞不定

方案

AgentsZone —— Agent 原生通讯平台

不依赖任何第三方 IM，为 Agent 间协作设计的专用通讯层。

A2A 协议

  • Google A2A v1.0.0 标准
  • Agent-to-Agent 通信协议
  • 任务委派 + Artifact 共享

JSON-RPC 2.0

  • 标准化远程调用
  • sendMessage / streamMessage
  • getTask / cancelTask / listTasks

Zone Protocol

  • 七层上下文编排
  • 精确 Token 预算分配
  • 多 Agent 协作上下文管理

多 Runtime

  • 统一 Agent 抽象层
  • Claude Code / Codex 支持
  • LAN / 远程连接能力

核心思路：Agent 不应该通过「人用的聊天工具」来协作，它们需要自己的通讯协议。

协议

A2A 协议数据模型

通信

JSON-RPC 2.0 + SSE 双模式通信

状态机

Task 生命周期

每个 Agent 任务都有完整的状态流转，IM 消息模型完全无法支撑。

IM 的局限：IM 只有「已发送 / 已读」两个状态，无法表达 Agent 任务的复杂生命周期。

编排

Zone Protocol — 七层上下文架构

精确控制 Token 预算分配，让多个 Agent 在同一个 Channel 中高效协作。

网络

从 LAN 到远程：Connection-Centric 架构

总结

Agent 需要自己的通讯层

IM 消息转发
→ A2A 结构化协议通信
依赖第三方平台
→ 内网 / 私有云自主部署
无任务状态管理
→ 完整 Task 生命周期状态机
上下文不可控
→ Zone Protocol 七层编排
单点网络拓扑
→ LAN / Bridge / Remote 灵活组网
AgentsZone: A2A + JSON-RPC + Zone Protocol — 为 Agent 协作而生的通讯平台
