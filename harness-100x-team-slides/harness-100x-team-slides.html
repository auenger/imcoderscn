Part 1

体感提效，还是真正提效？

同样的模型，同样的工具，不同团队交出了完全不同的成绩。

大多数团队：体感快了

  • PR 堆积、review 排队、bug 率没降反升
  • 写代码确实快了，综合生产力远没跟上
  • 还在用人类时代的旧流程指挥 Agent

极少数团队：真正提效

  • PingCAP CTO 用 AI 将 TiDB 兼容层重写为接近生产的 Rust 代码
  • Pigsty 创始人一人维护 460+ 扩展的 PostgreSQL 发行版
  • 日常同时调度十个 Agent 并行推进
Part 1

差距来自制度，不是模型

主流讨论集中在 prompt 技巧、工具选择和模型能力对比。这些有价值，但停留在操作层面，无法解释同一个工具在不同团队手里产生截然不同的结果。

真正提效的团队，都建立了与 AI Agent 特征匹配的工程制度。还在原地踏步的团队，依然在用为人类执行者设计的旧制度指挥 Agent。

"用人类时代的旧流程指挥 Agent，就像用马车交规管高速公路。"
Part 1

执行者变了，制度必须跟着变

六十年积累的制度体系——代码审查、测试策略、模块化、团队分工——是围绕人类认知特征设计的。

1
模糊之处 → 随机决策

人类用常识补全模糊需求，Agent 忠实执行输入，模糊变成随机

2
容量有硬上限 → 质量断崖

人类对复杂任务本能放慢，Agent 任务规模一大质量断崖下降

3
记忆止于会话边界

人类在项目中积累隐性知识并自然传递，Agent 每次都是"新员工的第一天"

4
10-100x 产出速度

放大了以上每一个问题的影响

路线图

两个基本原则

闭环

明确的规约定义输入，自动化验证检查输出，偏差被即时发现并纠正。恒温器、自动驾驶、工业流水线，所有需要可靠运行的系统都依赖反馈回路。

Agent 不会自我检查。反馈环必须被显式工程化到系统中。

演进

Agent 会忠实复制代码库中已有的模式，包括坏的模式。合并后的代码成为后续生成的参考集。

规约、测试、Skill 卡片、组织流程，每一层都需要持续演进。

闭环保证每一步可靠，演进保证系统越来越好。

三卷递进

卷一：可靠的 Agent 编程 — 个人提效

规约将模糊变为确定 → 自动化验证闭合反馈回路。你坐在 Agent 前面，产出从随机变为可靠。

卷二：规模化 Agent 开发 — 团队提效

跨会话记忆与上下文工程 → 多 Agent 并行的隔离与集成。从对话伙伴变成任务设计者和验收者。

卷三：治理百倍速的组织 — 组织提效

团队结构为什么失效 → 新的角色分工和治理模式。问题超越技术层面，进入组织设计领域。

卷一精华

规约与验证
从 Vibe Coding 到闭环工程

个人提效的核心方法论

卷一

Vibe Coding 是开环系统

凭感觉写 prompt，接受结果，觉得"看起来对"就过了。没有规约定义"对"是什么，没有自动化验证检查产出。

发出指令
→
接受产出
→
没有验证

开环系统在小规模下勉强可用。一旦项目需要长期维护和团队协作，随机性就不可接受了。

"代码生成速度彻底击穿了人类审查带宽。"
卷一

规约驱动：把模糊变为确定

不要直接说"修一下排序 bug"。花两分钟把需求结构化成规约：

## Bug: 订单列表排序错误

**预期行为**: 金额字段按数值大小降序排列
**当前行为**: 按字符串字典序排列（"99" 排在 "100" 前面）
**影响范围**: src/components/OrderList.tsx 的 sortFunction
**验证标准**:
  - [100, 20, 3] 应排序为 [100, 20, 3]
  - 修复后排序结果应为 [100, 20, 3]

"预期行为"告诉 Agent 目标，"影响范围"限定改动，"验证标准"是最后的闸门。

卷一

给现有功能加新逻辑

## Feature: 订单列表日期筛选

**新增文件**: src/hooks/useDateFilter.ts
**修改文件**: OrderList.tsx（仅筛选相关 props 和回调）
**不动**: 排序逻辑、样式文件、API 调用层
**验收标准**:
  - 默认不筛选，显示全部订单
  - 选择"最近 30 天"后只显示该范围内订单
  - 清除筛选恢复全部显示

"新增文件"告诉 Agent 在哪里写。"修改文件"限定改动范围。"不动"防止过度修改。验收标准是最后的闸门。

卷一

饱和式测试 + AI 生成用例

AI 擅长

  • 空值、undefined、超长字符串
  • 代码层面的边界值覆盖
  • 异常输入和极端 case

人擅长

  • 跨时区：服务器时间 vs 用户本地时间
  • 筛选 + 翻页交互的边界
  • 空状态的业务展示逻辑

AI 读 spec 生成测试场景清单，人 review 补上业务盲区，确认后交给 AI 写成测试代码。测试基建前置——在代码还没写的时候就把验证标准定好。

卷一

验证闭环

Spec
→
测试用例清单
→
测试代码
→
CI 自动执行
→
回归拦截

这条链路一断，Agent 就会积累错误。合并后的代码成为后续生成的参考集。没有持续验证，系统会自我强化地滑向退化。

Spec → Agent 执行 → 测试收口，跑通这条链路，你从 Vibe Coding 进入了工程模式。

卷二精华

规模化 Agent 开发
10 → 100x

团队提效：从陪聊到放手，从单 Agent 到多 Agent 并行

卷二

上下文崩塌：放手之后发生了什么

有了卷一的规约和验证体系，你才有可能放手让 Agent 自主执行。但放手之后，第一面墙是上下文。

1
上下文窗口有硬上限

大任务塞不进一个窗口，信息被截断或稀释

2
会话结束 = 记忆归零

昨天做过的决策、踩过的坑，今天全部重新来

3
上下文不是越多越好

无关信息会稀释关键信息，降低决策质量

卷二

解法：任务分解 + 上下文工程

分解
把大任务切成 Agent 能消化的块。每个子任务有独立的 spec 和验证标准，能在一个上下文窗口内完成。
筛选
上下文工程：只喂相关信息。文档、代码片段、历史问题——按需加载，不是一股脑塞进去。
持久化
跨会话记忆工程。通过文档、代码、历史问题合集建立共识。让 Agent 知道"病历本"，提升准确度并节省 Token。
工程化
Session 不是聊天记录。把执行单元工程化——任务级交接文档、进度文件、状态标记。
卷二

多 Agent 并行：隔离与集成

同时开两个 Agent 改同一份代码，冲突是确定的。各跑各的都对，合在一起就炸。

问题

  • 文件级冲突：两个 Agent 改了同一个文件
  • 语义级冲突：各跑测试都过，合并后翻车
  • 隐式依赖：Agent A 的输出被 Agent B 悄悄依赖

解法

  • 隔离：每个 Agent 独立分支、独立环境
  • 契约：接口先定义，各端按契约开发
  • 集成：CI 自动合并测试，冲突即发现
"搭跑道再放飞机——平台工程必须先于 Agent 并行。"
卷二

平台工程：多层反馈体系

放手让 Agent 跑，必须有可靠的反馈信号。不同时间尺度的反馈解决不同问题。

毫秒级：静态分析与代码规范

Agent 写完代码即触发 Linter、类型检查。格式和风格问题在此层拦截。

秒到分钟级：CI/CD 作为反馈通道

自动构建、测试、集成。合并请求必须通过全量测试才能合入。

分钟到天级：可观测性

部署后的监控、日志、告警。线上问题的快速定位和回滚。

Benchmark 驱动的反馈环

业务质量的度量：性能、准确度、覆盖率。用数据而非直觉判断系统状态。

卷三精华

治理百倍速的组织

团队结构正在瓦解，新的角色分工已经出现

卷三

团队结构为什么失效

"Leader 已经没办法 Leader 下属了，因为 Leader 可能还没下属会用 AI。"

传统模式

  • 前端、后端、QA、产品各管一块
  • 站会、评审会同步进度
  • Leader 管控下属
  • 流程为人类同步而设计

AI 原生模式

  • 一人 + Agent 打通全流程
  • 以代码提交强度和结果为准
  • 不受传统管理约束
  • 流程为 Agent 速度而设计
卷三

三角色分工模型

这三个人都不写代码。核心工作是定义问题、验收结果、编排流程。

PO
产品负责人

写高质量、自包含的 PRD

定义"做什么"

QO
质量负责人

定义验收标准和 Benchmark

确保"什么是对的"

TO
技术负责人

编排 Agent 工作流

负责"怎么做"

瓶颈已经不在代码生成。需求供给跟不上 Agent 的进度，变成 TO 每天追着 PO 要需求。

卷三

AI Pod：反脆弱的精英组织

划出小团队跑通流程，不受传统管理约束，以结果为准。

如果你想唤醒那些聪明但懒惰的员工，就让他去独立搞一条产品线。AI Pod 形成了一种"反脆弱"的小型精英组织。

小团队跑通
→
验证方法论
→
经验扩散
→
全团队复制
卷三

最大的坑：黑灯工厂

完全无人化的 AI 协作会导致代码风格不一致、理解偏差产生垃圾产出。看起来每个人都在省事，实际上系统在失控。

"不要相信'挂机写代码'的鬼话，工程永远是一件难受且充满对抗的事情。"

AI Coding 并没有发明新东西，它只是用极低的成本落地了那些早就知道、却因太贵而没执行的最佳工程实践。

铠铂云 · 实战案例

Playbook 方法论
在泛半导体 CIM 的落地

上海铠铂云信息科技有限公司

专注于泛半导体行业 CIM 系统整体解决方案
Kyber-MOM/CIM · Kyber-IIoT · Kyber Designer · Kyber ESG

案例一

企业知识基座：Jarvis Agent

铠铂云的核心挑战：泛半导体 CIM 系统涉及设备协议、工艺流程、错误模式等大量领域知识，散落在老工程师脑子里和各处文档中。新人上手慢，经验难传承。

接口协议库
→
设备行为画像
→
错误模式库
→
Jarvis Agent

做法（Playbook 卷二 · 记忆工程）

  • 将 36 项标准接口协议结构化为 Source Knowledge
  • 设备对接时同步积累型号响应基线
  • 运维排障时持续回写错误模式
  • 构建 Skill 体系：Source / Repo / Workflow

成果

  • 企业核心业务知识从"人脑"迁移到"Agent 可查"
  • 新场景开发不再从零开始，Agent 直接查询知识库
  • 知识飞轮：每次业务闭环都回写新知识，越用越准
  • 为后续两个 AI Pod 提供统一的知识基座
案例二

测机流程重构：2 人 AI Pod 实现 3-5x 提效

设备对接场景：厂商设备→测机服务→EAP 三端联调。传统模式靠老工程师凭经验排查，效率瓶颈明显。

改造前

  • 多人分工，靠经验排查三端问题
  • 错误定位靠人工逐端排查
  • 经验只在老员工脑子里

改造后：AI Pod（2人）

  • 1 名技术人员 + 1 名实施业务负责人
  • Agent 编排引导测试步骤、自动判定结果
  • Fail 时秒级定位错误端（设备/EAP/MES）

与 Jarvis Agent 关联：测机 Agent 查询知识库获取接口协议、设备画像、错误模式，实现编排辅助 + 三端快速诊断。设备对接场景下效率提升 3-5 倍。

案例三

LiteMES 新业务线：80-90% 代码自动化

面向中小工厂的轻量 MES 产品线。另一个 AI Pod 直接启动全新业务线，用 Harness 工作流进行完整开发。

Harness 工作流
规约驱动的完整开发流程。Spec 定义需求 → Agent 生成代码 → 自动化测试收口。非业务细节功能实现 80-90% 代码自动化编码和测试。
Skill 沉淀
针对 LiteMES 设计开发工作流 Skill。将产品线的通用开发模式沉淀为 Skill，后续交付直接复用于客户二次开发，实现快速拓展市场。

Playbook 卷二的核心实践：新业务线不是从零开始写代码，而是从 Skill 库中组合工作流。标准化功能的开发效率大幅提升，交付团队可以将精力集中在客户业务差异化上。

案例小结

铠铂云的 AI Pod 三步走

Jarvis 知识基座
→
测机 AI Pod（2人）
→
LiteMES AI Pod（新业务线）
1
知识先行。先建 Jarvis 知识基座，再让 AI Pod 消费知识。没有知识库的 Agent 就是空壳。
2
小团队验证。2 人 AI Pod 跑通一个业务场景，用结果说话，再扩散到其他团队。
3
Skill 沉淀复用。每个 AI Pod 的经验沉淀为 Skill，新业务线直接复用。这是从 3x 走向 30x 的关键。

铠铂云的实践验证了 Playbook 的核心论点：差距来自制度，不是模型。同样的 AI 工具，有规约、有知识基座、有 AI Pod 组织，个人提效→团队提效→组织提效的阶梯才能走得通。

收尾

行动清单

1
自己用。用 AI 做日常的事，体感不用不会有。不需要成为程序员，但需要理解"跟 AI 协作"意味着什么。
2
建立规约。从今天开始，每个 bug 和新功能都写 spec。先跑通闭环再追求速度。
3
投资测试基建。性价比最高的投入。测试基建差，Agent 产得越多债务积累越快。
4
找到你的 AI Pod。划出小团队跑通流程，验证方法论，再把经验扩散。
5
用 Playbook 持续学习。卷一规约验证、卷二规模化、卷三组织治理，按阶段进阶。
