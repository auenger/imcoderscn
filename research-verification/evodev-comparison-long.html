03
方法论映证

FDD 五阶段映射

EvoDev 将 FDD 经典五阶段抽象为三阶段，Feature-Workflow 实现了等价映射：

FDD 1
Build Overall Model → EvoDev: Overall Design → FW: /init-project + project-context.md
FDD 2
Build Features List → EvoDev: Feature Map Gen → FW: /new-feature + /split-feature
FDD 3
Plan by Feature → EvoDev: Feature Map Gen → FW: queue.yaml 依赖排序
FDD 4
Design by Feature → EvoDev: Iterative Dev → FW: spec.md 技术方案 + task.md
FDD 5
Build by Feature → EvoDev: Iterative Dev → FW: /implement-feature + /verify-feature

关键一致性：两者都遵循"先全局设计 → 再特性分解 → 按依赖迭代开发"的流程。FDD 的每个阶段都能在 Feature-Workflow 中找到精确的 skill 或文件对应。

Feature Map

Feature Map 结构映证

EvoDev: 单一 DAG

一个显式的有向无环图，每个节点包含三层上下文（Business / Design / Implementation），信息沿依赖边传播。

Feature Set A ← Business + Design + Impl
Feature Set B ← depends on A
Feature Set C ← depends on A, B

FW: 三文件组合等价

queue.yaml（动态 DAG 边）+ archive-log.yaml（历史节点）+ spec.md（节点内部三层上下文）

queue.yaml:     pending/blocked/active
archive-log.yaml: 55 completed nodes
spec.md:       3-layer context per node

05
上下文传播

三层上下文映证

EvoDev 论文

  • Business-layer：功能范围 + 接口定义
  • Design-layer：UI 组件 + 数据实体
  • Implementation-layer：代码变更记录
  • 信息沿依赖边自动传播到后续特性

Feature-Workflow spec.md

  • Description + User Value Points + Gherkin
  • Technical Solution + Context Analysis
  • Reference Code + Related Features + Archive Patterns
  • /start-feature 时加载前置特性的实现摘要

实际案例（feat-redesign-layout 的 spec.md）：

Related Features:
• feat-redesign-system (前置) — 提供 Bento Grid 设计令牌和 shadcn/ui 组件
• feat-p2-board-scaffold (已完成) — 建立了当前 layout.tsx，需完全重写
• feat-p2-e2e-playwright (已完成) — E2E 测试中有导航断言，布局变更需更新

Archive Implementation Patterns:
• 当前布局: Sidebar 使用 position: fixed w-60
• 页面路由: / /services /artifacts /knowledge-map /timeline

这正是论文描述的"通过依赖关系传播设计层和实现层上下文"的实际体现。

06
特性分解

特性拆分策略对比

EvoDev

  • Feature Extractor agent 自动分解
  • Feature Planner agent 按内聚性分组
  • 上限 4 个 Feature Sets
  • 未明确处理父特性
  • 拆分标准：功能内聚 + 依赖保持

Feature-Workflow

  • /new-feature: AI 分析用户价值点
  • 3+ 价值点时建议拆分
  • /split-feature: 按业务领域拆分
  • 父特性转为 module index（只读索引）
  • 拆分标准：按用户价值非技术层

Feature-Workflow 的超越：父特性转 module index 机制是 EvoDev 未涉及的创新点。拆分后父特性成为只读的子特性索引表 + 依赖图 + 进度跟踪器，保持了全局视角。

08
超越论文

Feature-Workflow 的 5 项创新

1. 物理隔离（Worktree-Based Isolation）

每个特性创建独立 git worktree，彻底消除并行开发时的文件冲突风险。EvoDev 在同一仓库中顺序开发。

2. 父特性 Module Index 机制

/split-feature 将拆分后的父特性转为只读索引（含子特性表格 + 依赖图 + 进度跟踪），EvoDev 的 Feature Map 未涉及。

3. 三文档递进收窄

spec.md (What) → task.md (How) → checklist.md (Done)，比 EvoDev 的单一 Feature Schema 更有层次感。

4. 归档即知识积累

archive-log.yaml + evidence/ 构成组织级知识库。55 个特性的实现细节、耗时、验证结果被完整保留。

5. 插件化分发

作为 company-ai-marketplace 标准插件，可跨项目复用。EvoDev 是研究原型，未考虑工业化。

09
理论启发

EvoDev 论文的启发价值

尽管 Feature-Workflow 在工程化上更成熟，论文提供了理论框架层面的启发：

形式化 Feature Map

论文将依赖关系明确为 DAG，形式化了三层上下文模型。可考虑从 queue.yaml + archive-log.yaml 自动生成可视化 DAG。

上下文传播形式化

论文精确描述了"信息沿依赖关系流动"。可考虑在 /start-feature 时自动注入所有前置特性的实现摘要，建立显式传播日志。

模型行为对齐问题

论文发现 Claude 系列倾向于多轮自编辑和修复，会提前实现后续迭代的特性。DevSubAgent 同样可能遇到此问题，应在 prompt 设计中加以防范。

迭代开发的成本效率

论文证明迭代开发在 GPT-4.1 和 Claude-3.5-Sonnet 上与单次生成成本相当，但产出质量更高。这与 Feature-Workflow 的实践经验一致。
