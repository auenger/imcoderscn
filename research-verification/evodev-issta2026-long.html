待验证原文

我们从经典软件工程中的特性驱动开发（FDD）方法中获得灵感，提出了一种特性驱动的迭代式端到端生成式软件开发框架 EvoDev。该框架引入了特性地图（Feature Map）作为演化式开发的核心组织结构，并利用特性依赖关系统筹开发任务规划以及上下文管理与传播……研究论文已被软件工程领域顶级国际会议 ISSTA 2026 接收。

03
内容验证

论文核心内容 与描述一致

FDD 灵感来源

论文第 2.2 节详细引用 FDD 方法论 (Goyal, 2007)，论述为何 FDD 适合适配到多智能体工作流。描述中"从经典FDD方法中获得灵感"准确。

Feature Map 概念

核心创新：Feature Map 是一个 DAG，显式建模特性依赖。每个节点包含 Business / Design / Implementation 三层上下文。描述中"引入特性地图"准确。

框架三阶段

① Overall Design Construction → ② Feature Map Generation → ③ Iterative Features Development。与FDD五阶段一一对应。描述中"迭代式端到端"准确。

实验结果

在 Android 开发任务上超越最佳基线 Claude Code 56.8%。单智能体提升 16.0%–76.6%。构建 APPDev 数据集（15个应用），耗费约 500 人时 + 1500 美元。

论文确实将 EvoDev 的 Feature Map 方法与 Claude Code 的线性 to-do 列表策略进行了对比："In contrast to the widely adopted linear planning strategies that merely produce a to-do list, our feature map captures the complex dependencies using a graph structure." — 描述中"不再将开发过程组织为线性的to-do列表"准确。

arXiv 版本 ACM 元数据分析

论文 arXiv 版本中包含以下 ACM 版权和元数据标记：

††copyright: acmlicensed

解读

  • acmlicensed：使用 ACM 版权模板，说明准备投往 ACM 会议
  • XXXXXXX 占位符：DOI 和 ISBN 未填写，说明 Camera Ready 尚未完成
  • 2018; Woodstock, NY：这是 ACM 模板默认值，不是实际会议信息
  • 作者收到接收通知后，需在 Camera Ready 阶段更新这些字段

推断

论文处于以下状态之一：

  • 场景 A：收到 Accept → 正在准备 Camera Ready → 尚未更新元数据
  • 场景 B：收到 Major Revision → 正在准备大修版本 → arXiv 版本未更新

两种场景都说明论文至少通过了初始审稿（未被直接 Reject）。
