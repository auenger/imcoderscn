问题

Vibe Coding：开环的陷阱

大多数团队用 AI 写代码的方式：写 prompt，看产出，觉得"差不多"就过了。整个过程没有验证环节。

模糊的指令
→
AI 自由发挥
→
凭感觉验收

Vibe Coding 的后果

  • Agent 对模糊处随机决策，改动范围失控
  • 产出快，但审查慢，PR 堆积
  • bug 率没降，技术债在加速积累

根本原因

  • 开环：发出指令 → 接受产出 → 没有验证
  • 用人类时代的流程指挥 Agent
  • 审查带宽被代码生成速度击穿
解法

Harness Engineering：闭环

结构化规约
→
Agent 受约束执行
→
自动化验证
→
偏差纠正

规约定义"对"是什么。自动化验证检查产出是否符合意图。偏差即时发现并纠正。闭环保证每一步可靠。

Vibe Coding

  • 凭感觉写 prompt
  • 接受结果，没有验证
  • 质量靠人肉 review

Harness Engineering

  • 结构化规约约束 Agent
  • 自动化测试验证产出
  • 质量靠 CI 和测试覆盖
流程重设计

瀑布 + 敏捷混合模式

Agent 时代不需要纯敏捷，也不需要纯瀑布。需要的是两者的混合。

瀑布
需求定义和架构决策 — 前端写清楚 spec、模块边界、API 契约。这些必须在上游定死，不能交给 Agent 随机决策。
瀑布
验收标准前置 — spec 带验收标准，代码还没写就把验证条件定好。测试基建前置。
敏捷
Agent 快速迭代执行 — 给 Agent 一个 spec，它端到端走完。不需要拆成前端、后端、测试再分别分配。
敏捷
持续验证和反馈 — CI 跑测试，不过就打回去。Agent 拿到反馈自动修复，再提交，再验证。
文档测试

针对文档进行测试

测试不光是测代码。更关键的是测文档，测规约本身是否完整、可执行。

通过实例化需求的方式，把模糊的业务描述变成可验证的实例。这些实例同时是需求文档、测试用例和验收标准。

## Feature: 订单日期筛选

**实例 1**: 默认状态 → 显示全部订单
**实例 2**: 选择"最近 30 天" → 只显示范围内订单
**实例 3**: 清除筛选 → 恢复全部显示
**实例 4**: 跨时区 → 以用户本地时间为准
**实例 5**: 筛选+翻页 → 第二页保持筛选状态

每个实例就是一个测试场景。文档写完了，测试清单也就出来了。

文档测试

语义推理：解决经验和认知的瓶颈

人的瓶颈

  • 个人经验有限，业务场景想不全
  • 系统复杂度指数增长，认知爆炸
  • 边界 case 总是事后补，来不及

AI 的补充

  • 基于 spec 语义推理，补齐遗漏场景
  • 技术边界（空值、类型、溢出）自动覆盖
  • 从实例化需求直接生成测试代码

AI 读 spec，通过语义推理枚举场景。人补上业务语境的盲区（时区、交互状态、空状态展示）。两份合并才完整。

质量量化

从验收标准到质量量化方案

光有测试不够，还得能量化测试本身的质量。

第一层
验收标准 — 每个 spec 附带可执行的验证条件。"没标准的 spec 是空白支票。"
第二层
覆盖度量 — 测试覆盖率、场景覆盖率。用数字说话，不用感觉说话。
第三层
质量趋势 — 追踪每个迭代的 bug 发现率、回归拦截率、测试通过率。看趋势，不看快照。
第四层
对抗性验证 — QO 用对抗性机制约束 AI：故意喂异常输入、边缘 case，确保测试套件真能拦住问题。
自驱动

循环自驱动

整个系统运转起来后，每个环节的产出都成为下一个环节的输入，形成自驱动的闭环。

结构化规约
→
Agent 执行
→
自动化测试
→
偏差反馈
→
修正规约
→
再次执行

代码→规约反馈

测试跑不过，偏差信息回填到规约。规约越来越精确，Agent 的产出质量同步提升。

规约→知识沉淀

每次修正的规约成为项目知识库的一部分。新任务开工前 Agent 先读"病历本"，避免重复犯错。

工程实践

Worktree：隔离、归档、可回溯

多 Agent 并行开发时，代码隔离是硬需求。Git worktree 为每个 feature 提供独立的物理工作目录。

隔离

  • 每个 feature 独立 worktree
  • Agent A 改文件不影响 Agent B
  • 依赖冲突天然隔离

归档 + 可回溯

  • feature 完成后归档 worktree
  • 出问题时秒级回溯到任意节点
  • 每个 feature 的完整变更历史可审计
新建 worktree
→
Agent 在隔离环境开发
→
CI 验证通过
→
合并归档

worktree 让并行开发从"小心翼翼地分支管理"变成"每个 Agent 各干各的，验证完再合"。这是多 Agent 并行的基建前提。

全景

从 Vibe Coding 到 Harness：一条路

1
写规约 — 把模糊需求结构化，附带验收标准。实例化需求让文档本身变成测试。
2
语义推理补全 — AI 基于规约推理测试场景，人补业务盲区。两份合并 = 完整测试清单。
3
Agent 在隔离环境执行 — worktree 隔离，受规约约束，改动范围可控。
4
自动化验证 + 质量量化 — CI 跑测试，覆盖率、拦截率、趋势看板持续跟踪。
5
偏差反馈 → 修正规约 → 自驱动循环 — 系统越转越精确。

收尾

  • Vibe Coding 是开环，Harness Engineering 是闭环
  • 流程重设计：瀑布管上游定义，敏捷管下游执行
  • 文档测试 = 实例化需求 + 语义推理，解决认知爆炸
  • 测试从"验收方案"升级为"质量量化方案"
  • 闭环自驱动：偏差反馈修正规约，系统越转越好
  • Worktree 隔离归档，多 Agent 并行的基建前提
"工程永远是一件难受且充满对抗的事情。Harness 要做的是让对抗可量化、可追溯、可自驱。"
