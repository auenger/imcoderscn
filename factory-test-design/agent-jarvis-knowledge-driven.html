Jarvis Knowledge-Driven Agent Design

业务知识驱动的 Agent 架构

引入 Jarvis 思想：Agent 的智能不来自硬编码规则，而来自业务闭环中持续积累的知识。接口协议、设备行为、错误模式——这些在测试过程中沉淀的资产，通过 Skill 体系结构化后，成为 Agent 编排辅助和错误诊断的"大脑"。

Jarvis 思想 · 知识驱动的 Agent
Agent 不是写死的规则引擎，是知识驱动的决策层
Jarvis 的核心：Agent-first 的组织能力层。Agent 能理解业务资产、路由到正确的系统、遵循真实工作流，并通过回写让知识复利增长。映射到测机场景：接口知识库、设备行为库、错误模式库就是 Agent 的"记忆"，Skill 是结构化访问这些记忆的方式。
传统方式：规则硬编码
问题：每种错误类型手写 if-else，新设备新接口就要改代码
问题：编排逻辑固定，换一条业务线就要重新开发
问题：经验只在老员工脑子里，不带走不走留
Jarvis 方式：知识驱动
做法：错误模式从真实测试中积累，Agent 查询知识库做匹配
做法：编排逻辑从业务知识中生成，新业务线只需要定义流程
做法：经验通过每次测试回写沉淀，越用越准

开发即积累 · 业务阶段就在建知识库
不是等 Agent 开发时才补课，是业务推进中同步沉淀
关键认知：Jarvis 不是 Agent 开发阶段才引入的东西。阶段一设备对接时就在定义接口协议——这就是 Source Knowledge 的起点。阶段二数据打通时就在记录设备响应特征——这就是设备画像的起点。阶段三三端联通时就在积累 EAP 行为数据——这就是错误模式库的起点。业务开发阶段如果不做结构化积累，到 Agent 阶段就是从零开始。
阶段一 设备对接测试
设备厂商点对点对接测机服务，逐接口调试。
同步积累：接口协议定义 + 设备型号初步特征
阶段二 测机 ↔ EAP 打通
原子化方法打通，实时通信，数据抓取展示。
同步积累：设备响应基线 + EAP 服务行为数据
阶段三 三端联通运维
三端解耦数据打通，业务场景监控，实时数据运维。
同步积累：错误模式记录 + 业务流程实践经验
知识沉淀
接口协议知识库
每对接一台新设备，就多一份接口协议定义。阶段一完成时，标准接口库已经成型。
设备行为画像
每次实时通信都在记录响应数据。阶段二完成时，主流型号的正常基线已经建立。
错误模式库
运维中每次异常处理都是一条错误记录。阶段三完成时，常见错误的归属和原因已有积累。
开发阶段不做积累，Agent 阶段就是从零开始
阶段一到三的每一步业务推进，都在产生结构化数据。关键是在开发时就用 Jarvis 思路做积累，而不是事后补文档。接口定义时同步建 Source Skill、设备对接时同步建画像、运维排障时同步记错误模式。等到了阶段四 Agent 开发时，知识库已经喂饱了，Agent 直接查询 Skill 就能工作——编排有流程模板可查，诊断有错误模式可匹配，不用从空库开始硬写规则。

知识资产 · Agent 的"大脑"
业务开发阶段已沉淀 + 持续回写增长
知识是 Agent 的燃料。前三阶段的业务开发已经在持续产生数据——接口协议定义、设备型号与响应特征、历史错误记录、EAP 服务行为。通过 Jarvis 思路结构化后，这些就是 Agent 的知识库。阶段四 Agent 不是从零开始，而是消费已经积累好的知识。
接口协议知识库
36 项标准接口（28 上报 + 8 下发）的完整定义：端点路径、请求格式、响应结构、超时阈值、校验规则。每新增一个自定义接口，知识库自动扩容。
Source Knowledge
设备行为画像
每种设备型号的正常响应基线：响应时间分布、数据格式特征、常见状态码、型号特有的协议偏差。Agent 靠这些基线判断"这次响应正常吗"。
Source Knowledge
错误模式库
历史测试中积累的结构化错误记录：错误特征 → 归属端 → 根因分类 → 处置方式。Agent 靠模式匹配定位新错误，而不是靠硬编码规则。

Skill 体系 · 知识的结构化访问层
Jarvis 思想：三类 Skill 覆盖知识访问、系统操作、流程编排
Jarvis 用 Skill 组织 Agent 的能力。Source Skill 让 Agent 查询知识库（接口协议、设备画像）；Repo Skill 让 Agent 操作系统（测机服务、EAP 平台）；Workflow Skill 让 Agent 编排业务流程（测试用例执行、错误诊断闭环）。Agent 不是写死的，是 Skill 驱动的。

Source Skills · 知识访问层

接口协议查询 Skill — 输入接口编号 → 输出端点、请求格式、响应结构、校验规则。编排辅助时"这条业务线涉及哪些接口"
设备画像查询 Skill — 输入设备型号 → 输出正常响应基线、已知偏差、常见问题。诊断时"这个型号的正常范围是什么"
错误模式匹配 Skill — 输入错误特征 → 输出历史同类错误、归属端、根因、处置方式。诊断时"之前有类似的错误吗"
业务流程模板 Skill — 输入业务场景名称 → 输出推荐步骤序列和每步待测接口。编排时"Panel 过站该测什么"

Repo Skills · 系统操作层

测机服务 Skill — 调用测机服务 API：发送测试指令、获取响应数据、查询设备状态
EAP 平台 Skill — 调用 EAP 自动测试平台：提交测试报告、查询验证结果、获取服务日志
数据采集 Skill — 实时抓取三端通信数据：报文、日志、状态、耗时

Workflow Skills · 流程编排层（Agent 的核心能力载体）

编排辅助 Workflow
Trigger：选择业务场景
Steps：查询流程模板 → 逐步引导操作 → 调用接口查询 Skill → 判定结果 → 提示下一步
Writeback：新发现的业务流程偏差 → 更新流程模板
错误诊断 Workflow
Trigger：测试节点 Fail
Steps：采集上下文 → 查询错误模式 Skill → 三端排查 → 原因排序 → 生成诊断报告
Writeback：新的错误模式 → 人工确认 → 写入错误模式库

Entry Skill · 测机 Agent 入口

角色定义：测机人员与 Agent 的唯一交互入口。接收自然语言或界面操作，路由到正确的 Workflow Skill 执行。
路由逻辑："帮我测 Panel 过站" → 编排辅助 Workflow；"这个错误是什么原因" → 错误诊断 Workflow；"查一下钻孔机的接口" → 接口协议查询 Source Skill。
回写职责：每次闭环结束后，将可持续复用的模式提升为知识，等待人工确认后写入知识库。

Agent 逻辑设计 · Skill 编排而非代码编排
Agent 的每一步决策都查询知识，而非执行硬逻辑
传统 Agent 把"钻孔机过站时该测什么"写死在代码里。Jarvis Agent 查询业务流程模板 Skill 获取答案——换了业务场景，Agent 代码不用改，知识库更新就行。这就是知识驱动的含义。

回写成长 · 知识复利
Jarvis 核心：真实闭环的 START → WORK → END 回写
Jarvis 不是生成一个漂亮的知识仓库就结束。真正的价值单位是一个可运行的闭环，在这个闭环里 Agent 能找到正确知识、帮助完成真实工作、把可持续复用的学习写回去。每次测试都是一次回写机会。
测试中回写
新错误模式 — 首次遇到的错误类型，诊断确认后写入错误模式库
设备基线修正 — 某型号的响应时间比已知基线偏移，更新画像
流程偏差发现 — 实际操作步骤与流程模板不一致，记录偏差
运维中回写（进化阶段）
生产环境新错误 — 测试中未覆盖的错误模式，生产中首次发现
设备老化特征 — 同一设备长期运行后的行为偏移趋势
跨产线知识复用 — A 产线的错误模式在 B 产线也适用
回写规则 · Jarvis 反模式约束
规则说明为什么
只提升反复出现的模式 一次性的偶发错误不写入知识库，出现 2 次以上才提升 避免噪音污染知识库，保证检索精度
记录可持续模式，不记流水账 "钻孔机过温 Alarm 处置方式"写进去，"今天下午 3 点测了什么"不写 知识库是模式库，不是日志库
人工确认后才写入 Agent 的诊断结论和建议由测机人员确认后才能进入知识库 Jarvis 原则：占位符和猜测不能当真相
不编造历史 不凭空生成"已知问题"或"决策记录"，只从真实闭环中提取 假历史毒害信任，Jarvis 明确禁止
真实 START→WORK→END 后才回写 一次完整的"启动测试→执行过程→输出报告"闭环结束后才写入 半途而废的数据比没有数据更危险

总结 · Jarvis × 测机 Agent
知识驱动，不硬编码
Agent 的编排逻辑和诊断能力来自结构化知识库，不是 if-else 规则。换设备、换业务线，知识库更新即可。

Source Skill 查知识、Repo Skill 操作系统、Workflow Skill 编排流程。Entry Skill 是唯一入口，路由到正确的 Skill 执行。
