Context 管理
1M 时代，最被低估的核心能力

窗口从 200K 涨到 1M，容量焦虑消失了。
但真正决定 AI 输出质量的，从来不是能塞多少，而是你往上下文里放了什么、没放什么、以什么顺序放。

杨正武 · 2026.06

真实场景

一个被反复验证的事实

🪲
你把整个项目丢给 AI，说「帮我改一下登录页面的 bug」。AI 迅速改完了登录页面，但顺手把旁边的支付模块也「优化」了一下。

它懂你的需求。但你的 context 里塞了太多跟登录页面无关的东西，它的注意力被稀释了。就像让一个人在嘈杂的工地里念电话号码，能听到，但记不全。

Context 的质量决定了 AI 输出的质量，而 context 的质量跟 token 数量几乎无关——1M 窗口只会让这件事更反直觉，不是让它消失。

核心认知

注意力是有预算的

误解：容器模型

Context window 是一个容器，窗口越大，能装的信息越多，AI 就越「了解」你的项目。1M 时代这个错觉尤其顽固。

真相：预算模型

Context window 是一个注意力预算池，每一条信息都在消耗这份预算。信息越多 ≠ 质量越好，往往恰恰相反。

你在 Cursor 或 Claude Code 里打开一个项目——当前编辑的文件、@ 引入的文件、项目结构、linter 错误、terminal 输出、git diff、system prompt——每一项都在消耗注意力预算。窗口从 200K 涨到 1M，预算池变大了，但每条信息消耗的预算一分没少。
论文实证

Lost in the Middle

2023 年 Stanford 等机构实验：把关键信息放在 context 的不同位置，测量模型回答准确率。

开头
~95%
中间
~55%
结尾
~90%

2026 年的新模型在长上下文检索上确实进步了，中间位置的衰减没那么夸张。但衰减的形状没变——首尾仍比中间可靠。当你把 1M tokens 一股脑塞给 AI，中间那段被「扫过去」的概率依然显著高于两头。

Self-attention 机制天然给首尾位置更高权重，这不是 bug，是 Transformer 架构的固有特性。模型在变好，但物理规律没变。

时代变化

1M 时代：窗口大了，问题没消失

从 200K 到 1M，有些事变了，有些事一点没变。分清楚这两类，是 2026 年做 AI 工程的基本功：

✓ 变了的

· 容量焦虑消失，不用频繁 /compact
· 系统占用占比从 25-50% 降到 5-8%
· 大文件、整仓库可以一次性读进来
· KV cache 命中带来的成本红利更显著

✗ 没变的

· 注意力仍是有限预算
· 首尾仍比中间更受关注
· 无关信息仍在主动拉低输出质量
· 需求偏离、context 污染照常发生

窗口变大解决的是「装不下」，没解决「看不清」。1M 时代真正的风险，是「反正装得下」这个念头本身——它让全塞进去变得零成本，于是所有人都开始全塞。

信噪比

Context 管理的本质

把 context 管理理解为 token 管理，是把问题想浅了。真正的 context 管理是在做信噪比优化——这件事跟窗口多大无关。

策略 A：大而全（1M 时代的默认诱惑）

  • 整个项目文件结构
  • bug 所在文件 800 行代码
  • 类型定义 + 测试文件
  • git diff + README + package.json
  • 「反正 1M 装得下，多塞点没坏处」

策略 B：精准裁剪

  • bug 相关函数 + 上下文（50 行）
  • 输入输出类型定义
  • 触发 bug 的测试用例
  • 一行项目背景说明

AI 在 50 行代码里找 bug，和在 800 行代码里找 bug，是完全不同的任务。前者它真的在读每一行，后者它大概率只扫了前 200 行和后 200 行。多塞的 750 行不是免费的，它们在稀释信号。

失败模式

需求偏离：最常见的翻车方式

需求偏离不是一步到位的，而是一个渐变过程：

Step 1
明确任务 — 给了一个清晰的需求
Step 2
顺便改改 — AI 觉得「一起改了会更好」
Step 3
牵连扩散 — 改了文件 A，文件 B 也需要调整
Step 4
继续顺便 — 新的 context 又触发了新的「顺便」
Step 5
彻底跑偏 — 你要的是改按钮颜色，AI 重构了整个组件体系

人类漂移了自己能意识到，AI 漂移了它完全不知道，还觉得自己做得很好。1M 窗口让「顺便改改」能波及的范围更大了。

1M 时代新失败模式

Context 膨胀：装得下，所以全塞了

200K 时代，物理上限逼着你做裁剪。1M 时代，这个外部约束消失了，一个新的失败模式取而代之：

1
无脑全量加载

整仓库 @ 进来，所有文档、所有历史对话都留着。「反正没超限」——但信噪比塌了。

2
注意力稀释

关键信息被埋在百万 token 中间，模型对它的「投入度」远低于你预期。检索得到 ≠ 真正理解。

3
成本与延迟静默上涨

1M 的 prefill 不便宜，cache miss 一次代价很大。膨胀的 context 让每次调用都更慢更贵，而你浑然不觉。

4
假性安全

因为「没报 context 超限」，你以为管理得很好。实际输出质量早就在悄悄下滑。

200K 时代你被迫学会的裁剪纪律，1M 时代要靠自觉保持。这是更难的事。

防御策略

怎么防住需求偏离与膨胀

缩小 context 边界

只给跟当前任务相关的文件和代码。「可能有用」和「确定有用」之间隔着巨大的信噪比差距。1M 不是不裁剪的理由。

显式声明约束

「只修改这个函数。不要重构。不要优化。只修 bug。」看似啰嗦，实际是在帮 AI 划定注意力边界。

分步执行 + 主动清理

大任务拆成小步骤，每一步只加载必要的 context。做完一步清掉无关上下文，再做下一步。别让历史无限累积。

及时纠偏

AI 开始「自由发挥」时马上打断。不要指望它自己绕回来。每发现一次偏离就是一次重新校准的机会。

工程模式

五个 Context 管理模式

1. 渐进式加载

不一次性塞满，按需加载。第一轮任务描述 + 核心文件，第二轮相关依赖，第三轮测试和边界情况。1M 时代依然成立。

2. 上下文裁剪

定期清理已完成、不再需要的上下文。已修复的报错？删。上个任务的讨论？删。用完的文档？删。

3. 结构化注入

不是堆砌，是有结构的组织：任务 → 约束 → 相关代码 → 测试用例。帮 AI 快速定位每部分的角色。

4. 场景隔离

A 项目偏好不带入 B 项目。昨天的临时决策不自动出现在今天。跨场景流动看起来像「智能」，实际往往是「污染」。

5. 上下文预算（1M 时代重定义）

预算不再是「别超限」，而是「别膨胀」。简单 bug 修复目标 1-2K tokens · 功能开发 5-10K · 架构重构 10-30K。一个简单修复塞了 200K？不是装得下就对了，是信噪比该检修了。

实战案例

Claude Code 的 Context 分层架构

Claude Code 的 context 不是静态字符串，是每次 API 调用时动态组装的六层结构：

L1
System Prompt — 身份声明 + 编码哲学 + 权限规则 + 风控约束，约 4-6K tokens
L2
Tool Definitions — 内置工具 + MCP 工具定义，约 20-50K tokens（MCP 按需加载 stub）
L3
CLAUDE.md + Memory — 全局 → 用户 → 项目 → 子目录，按层级拼接注入
L4
Dynamic Attachments — 日期、git status、plan 状态、技能列表，通过 <system-reminder> 注入
L5
Tool Visibility — 动态控制模型能看到哪些工具，不可见 = 不可调用
L6
Cache Optimization — 静态内容前置，动态内容后置，KV cache 复用率最大化（1M 时代这是省钱的核心）
Context 预算

1M 窗口下，你的输入去了哪里

同样是 Claude Code 的系统开销，在 200K 和 1M 两个时代占比天差地别（/context 命令输出）：

组成绝对量200K 时代占比1M 时代占比
System Prompt~4K2%0.4%
Tool 定义~20K10%2%
MCP 工具~26K13%2.6%
Memory / CLAUDE.md~4K2%0.4%
系统合计~54K~27%~5.4%

系统开销的绝对量没变（还是 50K 上下），但占比从 27% 掉到 5%。容量焦虑确实没了。但别高兴太早——这恰好意味着：你省下的 95% 空间，全靠你的自觉来守护信噪比，再没有物理上限替你兜底。

缓存经济学

静态内容（system + tools + CLAUDE.md）前置，共享 KV cache。1M 时代 cache 命中省下的钱更可观，cache miss 的代价也更痛。

Compaction 仍要做

1M 窗口让你更晚才触发自动压缩，但主动 /compact 的纪律依然有意义——压缩的不是空间，是噪声。

认知升级

从「写好 prompt」到「管好 context」

Prompt engineering 这个词容易让人产生错觉，以为 AI 工程的核心就是写好一段话。Prompt 只是 context 的一个组成部分。真正的能力在于：你知道在什么时间点，用什么结构，往 AI 的视野里放什么信息，不放什么信息。

这个能力的背后，是对注意力机制的直觉理解——1M 时代它只会更重要：

1
注意力是有限的

不可能同时关注所有信息，预算用完就没有了。窗口再大也是有限预算。

2
注意力是不均匀的

开头和结尾的信息天然获得更高权重，中间的容易被忽略。百万 token 里这点更明显。

3
注意力是容易被带偏的

一条无关的信息不只是浪费预算，它在主动拉低整体输出质量。塞得越多，带偏面越广。

结语

1M 窗口不是免责金牌，
注意力预算才是真相

窗口变大，免除了你「装不下」的焦虑，却把「管不好」的责任完全交还给了你。

做不好这件事的人，会在 1M 的「自由」里塞进整个世界，然后困惑 AI 为什么变笨了。
做好这件事的人，会在一百万 token 的余裕里，依然只给 AI 它真正需要的那五百行。

区别不在于窗口多大，在于你往它的视野里放了什么。
