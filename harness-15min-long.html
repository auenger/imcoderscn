2 / 11 挑战

五个问题，从单点到规模化依次暴露

用 AI 写代码，一开始感觉爽。但项目持续迭代，问题会沿着这条链路依次出现。

1
模糊处随机决策
Agent 对模糊需求忠实执行，模糊的地方全部变成随机决策。你写"修一下排序"，它改了排序、改了数据类型、还顺手重构了组件。
2
规约膨胀与演进困难
单个 spec 好写，spec 积攒多了，新 feature 要融入已有结构，老功能改了 spec 也得跟着改。规约库本身变成了需要维护的系统。Agent 会复制已有代码的模式，包括坏模式——spec 不更新，坏模式一代代传下去。
3
审查带宽被击穿
代码生成速度远超人类审查能力。PR 堆积，review 排队，bug 率没降反升。靠人肉 review 保质量这条路走不通了。
4
认知爆炸
系统复杂度指数增长，个人经验覆盖不了所有场景。边界 case 总是事后补，来不及。测试场景永远想不全。
5
并行冲突
多个 Agent 同时改代码，互相覆盖，依赖冲突。传统分支管理扛不住 Agent 级别的并行密度。
3 / 11 映射

每个挑战对应一个解法

方法论不是凭空设计的。每个工程实践都是为了解决上面那个具体问题。按"从单点到规模化"的顺序展开。

1. 模糊处随机决策
→
结构化规约 + 实例化需求
2. 规约膨胀 + 演进困难
→
瀑布+敏捷混合 + 循环自驱动
3. 审查带宽被击穿
→

4. 认知爆炸
→
语义推理补全测试场景
5. 并行冲突
→
Worktree 隔离归档

下面逐个讲：挑战是什么，为什么这个解法能解决它。

4 / 11 挑战 1

模糊决策 → 规约 + 实例化需求

问题

Agent 拿到模糊的 prompt，对模糊处随机决策。你说"修一下排序"，它改了排序、数据类型、还重构了组件。改动范围完全不可控。

为什么用规约

规约把"修什么""改哪里""不动什么""怎么验证"全部写死。Agent 没有自由发挥的空间，只能按规约执行。

实例化需求是规约的关键技巧：把模糊的业务描述变成具体的、可验证的实例。这些实例同时是需求文档、测试用例和验收标准。

## Feature: 订单日期筛选

**实例 1**: 默认状态 → 显示全部订单
**实例 2**: 选择"最近 30 天" → 只显示范围内订单
**实例 3**: 清除筛选 → 恢复全部显示
**实例 4**: 跨时区 → 以用户本地时间为准
5 / 11 挑战 2

规约膨胀 + 演进困难 → 瀑布 + 敏捷混合

问题
单个 spec 好写，spec 积攒多了，新 feature 要融入已有结构。老功能改了，对应的 spec 也得跟着改。软件持续演进，规约库本身也变成了需要维护的系统。而且 Agent 会忠实复制代码库里的模式——spec 不更新，坏模式就一代代传下去。
解法
上游用瀑布，下游用敏捷。新功能的需求定义、架构决策、验收标准必须在 Agent 上手之前定死——这是瀑布的部分。定好之后 Agent 拿到 spec 快速迭代执行，CI 持续验证——这是敏捷的部分。
为什么
纯瀑布太重，改一次需求就要走一遍完整流程。纯敏捷太松，没有上游约束 Agent 就乱来。spec 越积越多这个场景下，需要瀑布的严谨来守住上游，敏捷的节奏来驱动下游。

瀑布管"新功能怎么定义"，敏捷管"Agent 怎么执行和验证"。两者搭配，规约库才能跟着软件一起演进，而不是越积越烂。

6 / 11 挑战 3 & 4

审查击穿 + 认知爆炸 → 文档测试 + 语义推理

spec 解决了"怎么写需求"，瀑布+敏捷解决了"怎么组织流程"。但 spec 写了之后，验证怎么办？

问题
代码产出速度远超人类审查能力，人肉 review 保质量这条路断了。同时系统复杂度指数增长，个人经验覆盖不了所有测试场景，边界 case 总是事后补。
解法
针对文档进行测试——测试不光是测代码，更关键的是测文档本身。通过实例化需求让每条规约自带验证条件，文档写完了测试清单也就出来了。
解法
语义推理补全——AI 读 spec，通过语义推理枚举场景。技术边界（空值、类型、溢出）自动覆盖。人补业务语境的盲区（时区、交互状态、空状态）。两份合并才完整。

AI 擅长技术边界，人擅长业务边界。文档测试 + 语义推理的组合，把"个人经验和认知覆盖不了"这个瓶颈给解了。

7 / 11 深化

测试本身的质量怎么衡量

上面解了"怎么测"的问题。但光有测试不够——测试本身的质量也得量化，否则就是形式主义。

第一层
验收标准——每个 spec 附带可执行的验证条件。没标准的 spec 就是给 Agent 发空白支票。
第二层
覆盖度量——测试覆盖率、场景覆盖率。用数字说话，不用感觉说话。
第三层
质量趋势——追踪每个迭代的 bug 发现率、回归拦截率、测试通过率。看趋势，不看快照。
第四层
对抗性验证——QO 故意喂异常输入、边缘 case，确保测试套件真能拦住问题，而不是只测 happy path。
8 / 11 自驱动

循环自驱动：让规约库自己转起来

规约、流程、测试都讲完了。但纠错不能靠人盯着，得让系统自己转。

结构化规约
→
Agent 执行
→
自动化测试
→
偏差反馈
→
修正规约
→
再次执行

代码→规约反馈

测试跑不过，偏差信息回填到规约。规约越来越精确，Agent 的产出质量同步提升。

规约→知识沉淀

每次修正的规约成为项目知识库的一部分。新任务开工前 Agent 先读"病历本"，避免重复犯错。规约库随着迭代越来越精确，坏模式被自动清洗。

9 / 11 挑战 5

并行冲突 → Worktree 隔离归档

问题

多 Agent 同时改代码，互相覆盖，依赖冲突。传统分支管理扛不住 Agent 级别的并行密度。一个 Agent 改坏的东西会影响另一个。

解法

Git worktree 为每个 feature 提供独立的物理工作目录。Agent A 改文件不影响 Agent B。完成后归档，出问题秒级回溯。

新建 worktree
→
Agent 在隔离环境开发
→
CI 验证通过
→
合并归档

并行开发从"小心翼翼地分支管理"变成"每个 Agent 各干各的，验证完再合"。这是多 Agent 并行的基建前提。
